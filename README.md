# Бронь без конфликтов

**Учебный проект** по дисциплине «Проектирование и разработка веб-приложений».

## Назначение
Веб-сервис для бронирования ресурсов образовательной организации (переговорные комнаты, аудитории). Сервис гарантирует, что один ресурс нельзя забронировать на пересекающееся время.

## Стек технологий
- **Backend:** Node.js, Express
- **База данных:** PostgreSQL (pg)
- **Аутентификация:** JWT (jsonwebtoken, bcryptjs)
- **Frontend:** HTML, CSS, Vanilla JavaScript
- **CI/CD:** GitHub Actions

## Роли пользователей
- **Пользователь:** просмотр каталога, создание своих броней, отмена своих будущих записей, просмотр только своих записей.
- **Администратор:** всё то же + просмотр всех записей и владельцев, отмена чужих записей с обязательной причиной, управление ресурсами, просмотр аудита.

## Правила времени (бизнес-логика)
- Ресурсы доступны ежедневно с **08:00 до 22:00** (МСК).
- Шаг выбора времени: **30 минут**.
- Продолжительность брони: от **30 минут до 4 часов**.
- Начало брони не в прошлом и не позднее чем через **30 суток**.
- Бронирование целиком помещается в один рабочий день.
- Конфликт: `[начало1, конец1)` и `[начало2, конец2)` пересекаются, если `начало1 < конец2 И конец1 > начало2`.
- Отменённые записи не занимают время.

## Защита от конфликтов (Шаг 12)
Используется **транзакция с блокировкой строки ресурса** (`SELECT ... FOR UPDATE`) в `src/services/reservation-logic.js`. Пока один запрос блокирует ресурс, второй ждет. После завершения транзакции второй проверяет конфликт заново и получает `409 Conflict`.

## Защита от дублей (Шаг 16)
Клиент передает заголовок `Idempotency-Key`. Сервер сохраняет ключ в таблице `idempotency_keys` в одной транзакции с созданием брони. Повторный запрос с тем же ключом возвращает исходную бронь без создания дубликата.

## Схема базы данных
Создаётся из файла `database/init-tables.sql` (5 таблиц: `users`, `resources`, `bookings`, `idempotency_keys`, `audit_logs`).
